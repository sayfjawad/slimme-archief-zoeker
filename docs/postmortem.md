# Building a smart, context-aware archive of Dutch politicians: approach, hardware, sources, and what actually went wrong

*Written 2026-07-25. Covers the build-out of [slimme-archief-zoeker](https://github.com/sayfjawad/slimme-archief-zoeker) (formerly wilders-search) — live at wilders.scrib-r.com and yesilgoz.scrib-r.com — and the sibling project abo-ali-search, which shares its architecture, hardware and several of its hardest lessons.*

This is not a highlight reel. The point of writing it down is the failures: several of them cost real hours, one of them briefly destroyed a live, public dataset. If you're building something similar, the fastest way to skip our mistakes is to read section 5 first.

---

## 1. What this is

A pipeline that collects everything a public figure has said — official government transcripts, historical records, and video appearances — parses it into a searchable, timestamped archive, and serves it through a semantic (meaning-based, not keyword) search interface with an optional RAG-style AI summary. Every result links back to a playable moment in the original source, so a claim can always be checked against the primary record.

Two live instances of the Dutch-politician variant exist so far (Geert Wilders, Dilan Yeşilgöz), architected from the start to share data across politicians rather than duplicate it. A sibling project, abo-ali-search, applies the same architecture to a single Arabic-language public figure and predates the multi-politician work — several of its components (the diarization pattern, the Wilders-project's own bootstrap) were reused directly.

## 2. Data sources

| Source | What | How obtained | Notable gotchas |
|---|---|---|---|
| **Tweede Kamer OData** (`gegevensmagazijn.tweedekamer.nl`) | Official, corrected parliamentary transcripts (vlos 2.0 XML), 2013–present | Open API, no key. Downloaded **unfiltered** — every verslag, not just ones mentioning a tracked politician — because it's cheap and makes the archive genuinely shared from day one | `$top` caps the *total* result count and silently suppresses `@odata.nextLink` — omit it and follow server-side paging (250/page) instead, or you'll think you've got everything and you haven't |
| **Handelingen 1995–2013** (`officielebekendmakingen.nl` SRU) | Pre-OData-era parliamentary record | SRU search **filtered by person name** per politician (unlike the TK feed, not bulk) | 429 on unthrottled bulk fetch — needs a real delay between requests |
| **YouTube — party channels** | A politician's party's own channel content | `yt-dlp`, audio-only (`opus`), `--download-archive` for incremental sync | Rate-limited within minutes without `-t sleep` between requests. **Not curated content** — it's the entire channel, unfiltered: campaign ads, holiday greetings, and clips of *other* politicians from the same party end up in the pool, mislabeled unless diarization sorts it out (see §5) |
| **Debat Direct video** (`debatdirect.tweedekamer.nl`) | Plenary session recordings, ~2010–present | Agenda API gives per-day sessions; each debate's HLS `vodUrl` only yields real footage when windowed with `?start=&end=` query params (otherwise a "nomeeting" stub) — lowest-bandwidth video + separate audio rendition, stream-copied | Committee-room sessions (not `plenaire-zaal`) have no video at all — a real, permanent gap, not a bug (cost real debugging time to confirm, see §5) |
| **Abo Ali's public output** | A different figure's content — historical archive was YouTube, **current output is a 24/7 live stream**, not on-demand video at all | Historical: `yt-dlp` against the channel. Current: raw `ffmpeg` HLS capture of a fixed daily window on the source's CDN (`bozztv.com`) | The live-vs-VOD distinction wasn't obvious until we tried to build an incremental downloader and found the "episode" was one un-ending stream — see §5 |

## 3. Hardware

Everything runs on owned hardware over a private Tailscale mesh — no cloud GPU rental, no per-token API costs.

- **HP Z8 G4 workstation** (dev + orchestration host) — 2× Tesla V100 32GB + 1× Quadro K2200 (too old for current PyTorch, unused for compute). Runs the politician-search apps as systemd user services, drives the distributed download/transcription orchestration.
- **Dell C4130** (`c4130-4xv100`, production node) — 4× Tesla V100 32GB. Runs the sibling scrib-r platform's live production workers (docker-compose: 3 GPU workers, 2 CPU workers, 2 reasoning workers, a local llama.cpp instance) *and* abo-ali-search's live app — one GPU is typically free for batch work, the other three are shared with production and were deliberately avoided for anything heavy.
- **ARM node** (`gx10`, aarch64, NVIDIA GB10 unified memory) — borrowed for transcription shards via a proven Docker-based remote-worker pattern (`docker run --gpus all` against a known-working image, since native aarch64 wheels for some ML libraries are unreliable).
- **Small edge VPS** — nginx + TLS (Let's Encrypt/certbot) reverse-proxying every public subdomain over Tailscale to whichever internal host actually serves it. Wildcard DNS on the shared domain means a new politician's subdomain needs zero DNS work.
- A 4×P100 node exists on the same network but was never brought into service — its iDRAC management interface is locked out (three credential guesses, all rejected) and fixing that was never worth the payoff versus the hardware already in use.

Nothing here is exotic. The V100 is a 2017 GPU. What made the timelines short was reuse, not raw horsepower — see §6.

## 4. Techniques

- **ASR**: WhisperX (`large-v3`), batch-oriented, GPU-accelerated.
- **Diarization**: pyannote.audio, called via its **Python API directly** (not WhisperX's built-in `--diarize` CLI flag — see §5 for why that distinction mattered). Convention: for single-uploader content (a party channel, a solo broadcaster), the diarized voice with the most total airtime in a given recording is labeled as that person; every other detected voice stays an anonymous `SPEAKER_NN` — cheap, and correct for this content shape without needing voice-print enrollment against a reference.
- **Embeddings / semantic search**: BGE-M3, GPU-embedded, served through a FastAPI app with SQLite for structured data and a flat `.npy` array for vectors (no vector database — the corpus is small enough that this is simply faster and has zero moving parts).
- **RAG answers**: an optional local llama.cpp instance (Qwen2.5-14B), auto-discovered if present; the app degrades gracefully to search-only if no LLM endpoint is reachable.
- **Distributed downloading**: HLS video and audio are stream-copied (no re-encode) via `ffmpeg`, sharded by a simple `index % N` split across every available host, coordinated by a puller process that drains remote output back to a shared store. 8-way sharding across 4 hosts took a 326-debate-day video backlog from an estimated multi-week job down to about five days.

## 5. Failures and near-misses — the part worth reading

Roughly chronological. Each of these cost somewhere between "an annoying hour" and "half a day," except the one marked critical, which cost a live dataset for about twenty minutes before being fully recovered.

**5.1 — `$top` silently truncates OData pagination.** Early on, a naive query with `$top` set appeared to work — until the counts didn't match reality. `$top` caps the *total* result count across all pages and, in doing so, suppresses `@odata.nextLink`. Omit it; let the server paginate at its own page size and follow the link.

**5.2 — YouTube rate-limiting without a throttle.** A bulk channel download without `-t sleep` between requests got the session rate-limited within minutes — zero further downloads, no useful error. Fixed by always passing `-t sleep`; the tradeoff is that a large channel takes hours, not minutes, but hours beats zero.

**5.3 — ffmpeg refusing HLS segments on newer versions.** ffmpeg ≥7/8 rejects a CDN's `.m4v`-extension HLS segments under its default, stricter extension allowlist (`"extension mismatches allowed extensions"`). This affected one host (Ubuntu 26.04) and not others (older ffmpeg on the rest) — inconsistent behavior across otherwise-identical shards until the version difference was spotted. Fix: detect and pass `-allowed_extensions ALL -extension_picky 0` when the installed ffmpeg supports those flags.

**5.4 — ffmpeg can hang forever on a stalled live/long-running HLS read.** Two multi-hour "marathon" debates (a coalition-formation debate, a COVID-era session) caused ffmpeg to hang for 24+ hours with sockets stuck in `CLOSE-WAIT` after the source CDN half-closed a connection mid-download without ffmpeg noticing. Because shards process their assigned dates sequentially, one hung download **silently blocked every later item behind it** — a shard that looked "still running normally" in a process list had actually been dead-in-the-water for most of a day, no crash, no error, nothing to alert on. Fixed with `-rw_timeout` per input plus a hard subprocess timeout as backstop. **Lesson: "the process is still running" is not evidence of progress — check that output is still growing before trusting a long download.**

**5.5 — orphaned ffmpeg children survive their parent's death.** `kill <pid>` on a Python download-orchestrator process only signals that process, not the `ffmpeg` child it spawned via a plain subprocess call (no process-group setup) — the child is reparented to init and keeps running as an orphan. After a shard restart, an orphaned ffmpeg from the *previous* run was found still writing to the same output filename a *freshly started* shard also claimed — a live data race, two processes writing one file, caught by inspection before it corrupted anything. Fixed by reaping any ffmpeg reparented to init (and its now-stale partial output) before starting or restarting a shard, on every host, not just the one being touched.

**5.6 — a remote-launch pattern hung for eleven hours.** Starting a detached background process on a remote host over SSH (`ssh host 'nohup long-running-thing &'`) can hang the SSH session itself waiting on inherited file descriptors, even though the remote command *did* start correctly — the connection just never returns. This silently stalled a batch of remote download shards for eleven hours before being noticed (nothing crashed; the orchestrating script was just sitting there). Fix: launch inside an explicit subshell — `ssh host '(nohup thing &); exit 0'` — so the remote shell exits immediately regardless of what the detached process is doing.

**5.7 — accidentally stopping a live production container.** While cleaning up a crashed *test* Docker container (launched with `--rm`, which had already self-removed after failing on a bad argument), a cleanup command filtered containers by *image* (`--filter ancestor=<image>`) rather than by exact container name. The filter matched — and stopped — the actual **live production instance** sharing that same image, three days into its uptime. Caught within seconds via the running-container list, restarted immediately (its restart policy required a manual `docker start`, since a `stop` doesn't count as a crash). **Lesson: on a host running both production and test workloads, never target Docker operations by image/ancestor — always by the exact container name, and give test containers an explicit unique name so they're unambiguous to find.**

**5.8 — a service outage that "fixed itself," then reappeared, from the wrong cause.** A separate app's AI-answer feature started failing with a plain connection-refused error. The first hypothesis — a stale cached IP address for a peer Docker container, following directly from the incident above — was plausible, looked fixed after a service restart, and was reported as fixed on the strength of an HTTP 200 response. It wasn't: **an HTTP 200 with a JSON body containing `{"error": "..."}` still counts as a broken response**, and the truncated response glance used to "confirm" the fix happened to land on a part of the payload that wasn't the error field. Caught only because the fix was double-checked rather than accepted at face value. The real cause, found afterward: a **hardcoded environment-variable override** in that service's systemd unit pointed at a port nothing had listened on since an earlier architecture migration, silently shadowing the service's own working auto-discovery logic. **Lesson: parse the actual response payload's success/error field before calling anything fixed — a status code alone proves nothing for an endpoint that can return 200 with an error body. And when a service has both a hardcoded override and a working fallback, check the override for staleness before debugging the fallback.**

**5.9 — a stale on-disk config that had drifted from the running config.** Separately, a reverse-proxy config file on disk pointed at the wrong backend host entirely — but the *running* nginx process still had the old, correct value loaded from before some earlier, never-reloaded edit. The service worked by accident; the very next routine reload or restart would have broken it with no warning. Found only by deliberately diffing the on-disk file against nginx's actual in-memory configuration (`nginx -T`) rather than trusting either one alone.

**5.10 — a broken host-level GPU driver, unrelated to anything we'd touched.** Mid-session, launching a *new* GPU container started failing while every *already-running* GPU container kept working fine. Root cause: an unattended system package upgrade had bumped the userspace NVIDIA driver tools without reloading the matching kernel module — already-established GPU contexts survived, but nothing new could be created. Diagnosed via the specific error chain (`nvidia-persistenced` failing to query devices, not a permissions issue despite a permissions-shaped error message). Fixed with a full host reboot after confirming every production service was correctly configured to auto-recover (systemd `enabled` + Docker `unless-stopped` restart policies) — verified completely healthy afterward. **Lesson: "it fails for new things but old things still work" is a strong, specific signature of a driver/userspace version mismatch — don't waste time on permissions or networking theories first.**

**5.11 — [CRITICAL] a rebuild step wiped a live, public dataset down to one entry.** The most serious incident. An index-rebuild script does a full rebuild from source transcript files each time it runs — by design, since that's simpler than incremental updates. Testing a new pipeline against that rebuild step revealed, too late, that **the actual source transcripts for 2,519 of 2,523 archived videos no longer existed anywhere on the serving host** — only the compiled search index and the raw video files had survived from whatever earlier work originally built it; the intermediate transcript JSON had been cleaned up at some point as a disk-space measure, with nobody registering that this made the compiled index the *only* copy of months of transcription work. The rebuild ran, found only the one new test file, and the live index dropped from 2,523 videos to 1 — instantly, publicly, with no confirmation prompt because none of the surrounding tooling expected a rebuild to be destructive.

Recovery: no backup existed on the serving host, in git, or in any snapshot mechanism. A thorough, explicitly-requested wider search across every other host on the network turned up a complete, undocumented copy of the missing transcripts on a third machine — nobody had a record that this copy existed; it was found by chance because the search was widened past the "obvious" places. Restored in full within the hour; verified with a real content query, not just a status check (see 5.8's lesson — applied correctly, this time).

**Fix, made structural rather than a one-off patch:** every rebuild script (across every project sharing this architecture) now backs up the current compiled index before overwriting it, unconditionally, inside the tool itself — not as an optional wrapper someone could forget to call. A separate daily job mirrors the actual source transcripts (the expensive, hard-to-regenerate asset) to a dated backup location with a two-week retention window, wired into both the crash-recovery path and an independent daily cron entry so it runs regardless of whether anything else does. **The single biggest lesson of this entire project: a destructive step should never be reachable without a backup existing first, and "we'll add backups later" is exactly the sentence that precedes losing something. Bake it into the tool, not into a habit.**

**5.12 — a live stream mistaken for an archive.** Building automation for new content from Abo Ali's current output, the initial plan assumed a downloadable video-on-demand archive, matching the historical YouTube pattern. The actual source turned out to be a continuous, unending 24/7 live stream (confirmed directly: the HLS manifest's internal stream naming was literally `live40_...`, and a fluctuating live-encoder bitrate broke a first extraction attempt that had hardcoded an exact bandwidth value from one manifest fetch). Recording a live stream is a materially different problem from downloading a VOD file — it needs a scheduled capture window, not a `download-archive` incremental sync — and the fix required asking rather than guessing: nothing in any existing script or log documented the correct daily broadcast window, so the actual schedule had to come directly from the person who knew it.

**5.13 — a shared frontend silently mislabeling a second instance.** Two live app instances share one frontend codebase, differentiated only by a backend config value. The backend was correctly person-aware from day one — but the static page itself had the *first* politician's name hardcoded into the page title, hero text, and body copy, so the second instance served **correct search results under the wrong person's name and photo**. This passed an initial verification because that verification checked only the JSON API response, never the rendered page a human would actually see. **Lesson, same shape as 5.8: verifying the data layer is not the same as verifying the user-facing output — when multiple deployments share one frontend, always check the actually-rendered page (not just the API) for each instance.**

**5.14 — an apparent sharding bug that was a real, permanent data gap.** After a distributed download run reported all shards complete, seven expected video files were missing with *no* error logged anywhere — not "download failed," not "no footage available," nothing, across every worker's log. The first hypothesis was a bug in the parallel-shard splitting logic. The actual cause, confirmed by querying the source agenda API directly for those specific dates: the relevant sessions were held in committee rooms, not the main chamber, which the video source doesn't cover at all — the download script's own logic correctly produces *no output whatsoever* (not even a "skipped" log line) for a day where nothing matches its location filter, which look identical to a silent bug unless you go check the source data directly. Nothing was wrong; the coverage ceiling (97.5%) was real and final. **Lesson: before assuming your own code is broken, check what the source data actually contains for the specific cases that are missing.**

## 6. What actually worked, and why it went fast

The distinguishing factor across this whole build was **reuse of prior, hard-won work** over reinventing it:

- A near-identical diarization implementation already existed in a sibling project, built and proven at scale months earlier. The first attempt at diarization for this project ignored that and used a different (broken, on this hardware) library path — reverting to the sibling's proven pattern fixed it immediately, with zero further library-version debugging.
- The shared-transcript-pool architecture meant the second politician's onboarding reused the majority of already-downloaded parliamentary data outright — measured directly: 62% of relevant debate transcripts and 30% of relevant debate video needed zero new work.
- Every download step (parliamentary text, video, YouTube audio) is idempotent and resumable by design — a crash, a reboot, or a deliberate interruption never loses partial progress, it just picks back up.
- Docker images and model caches already validated for one host were copied wholesale to a second host rather than re-derived from scratch, avoiding a repeat of dependency-version debugging in a new environment.

The pattern that comes out of all of this, both the wins and the incidents: **check whether the problem in front of you has already been solved somewhere in the same family of projects before treating it as new** — and **never let a destructive operation run without a backup existing first, as a property of the tool, not a step someone has to remember.**
